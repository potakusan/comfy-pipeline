# シード引き継ぎのプロンプト継承拡張 ＋ プロンプト変数バインディング

対応issue: 未起票（本提案が確定したら feature_spec で起票する）

## 背景

直近のコミット（#59 系）で「販売用選択画像のseedを一括キューへ引き継ぐ」機能を入れた。現状の挙動は次の通り。

- アーカイブ（`.seed-archive/`, [gallery-seed-archive.ts](../../lib/server/gallery-seed-archive.ts)）が永続化するのは `seed` / `upscaleSeed` / `batchPresetId` / サムネのみ。**プロンプト本文も「どのランダム行が当たったか」も保存していない。**
- 引き継ぎ実行時、プロンプトは引き継ぎ先で選んだセット/プリセット＋overrides（可変LoRA・身体的特徴・シーン）から**完全に再構築**される。プールからは各バッチに `seed` / `upscaleSeed` を固定注入するだけ（[use-pipeline-queue.ts:299-312](../../hooks/pipeline/use-pipeline-queue.ts#L299-L312)）。
- `promptMode:"random"` のプリセット行・`additionalPromptMode:"random"` の1行・`variationTags` は**バッチごとに `Math.random()` で引き直し**（[use-pipeline-queue.ts:185-192](../../hooks/pipeline/use-pipeline-queue.ts#L185-L192), [266-290](../../hooks/pipeline/use-pipeline-queue.ts#L266-L290)）。画像seedはKSamplerのseedであって、JS側の抽選には影響しない。

つまり現状の「引き継ぎ」は数値seedだけの引き継ぎで、狙った画像の“中身”（構図を作っているランダム選択）は引き継がれない。実運用では「元画像の雰囲気・小物・ポーズ傾向はそのままに、キャラ（可変LoRA・体型・シーン）だけ差し替えた別バリエーションが欲しい」という要求があり、そこにギャップがある。

## 用語整理

| 呼称 | 実体 |
|------|------|
| プリセットスロット | `physical`（身体的特徴・複数）/ `count` / `pose` / `scene` / `other`（その他・複数）。[comfy-types.ts:34-53](../../lib/comfy/comfy-types.ts#L34-L53) |
| ランダム１行 | `additionalPromptMode:"random"` で追加プロンプト欄から1行抽選するもの。`promptMode:"random"` のプリセット（テキスト塊から1行抽選）も同種 |
| バリエーション | `variationTags` から1個抽選して末尾に付与するもの |
| 変数 / プレースホルダ | 本提案で新設。プリセットや追加プロンプトのテキストに `%%name%%` と書き、生成時に具体値へ解決される名前付きの穴 |
| バインディング | 変数名 → 解決値（＋解決モード）の対応。生成時に確定し、記録・引き継ぎの対象になる |

## 現状整理（引き継ぎ元→引き継ぎ先で何が起きるか）

| 要素 | 現状 |
|------|------|
| 可変LoRA / 身体的特徴 / シーン | 引き継がず、引き継ぎ先の RunSetupView で選び直す（overrides） |
| `count` / `pose` / `other` プリセットの**選択** | `batchPresetId` から元の一括セットを自動特定（#62 de9727e）。同じプリセットを選べば選択は一致する |
| `promptMode:"random"` の当たり行 | 引き継ぎ先で `Math.random()` により**引き直し**。元画像と揃わない |
| ランダム１行（`additionalPromptMode:"random"`） | 同上。引き直し |
| バリエーションタグ | 同上。引き直し |
| アイテム単位の書き換え | 仕組みなし |

## 要件

ユーザーの要求を4点に整理する。

1. **可変LoRA・身体的特徴・シーンは引き継ぎ先で異なりうる** — 現状の設計（引き継がず選び直す）で満たしている。**変更不要**。
2. **「その他」およびランダム１行のランダム要素は、原則として引き継ぎ元と同一の結果を使いたい** — 未実装。引き継ぎ元でどの行/タグが当たったかを記録し、引き継ぎ先で再生する必要がある。
3. **「その他」の一部アイテム（服のはだけ具合など）は、引き継ぎ元の値をそのまま使えない** — 引き継ぎ元が `dress lift` / `dress pull` でも、引き継ぎ先キャラの服装によっては `shirt` 系・`swimsuit` 系など別パターンになる。引き継ぎ先の服装コンテキストに応じた読み替えが要る。
4. **引き継ぎ元プリセットのアイテムの一部だけを書き換えたい** — その書き換えは、同じアイテムが選択されている全プリセット／全バッチに一括適用したい。

## 中核設計: プロンプト変数バインディング

プリセット／追加プロンプトのテキストに `%%name%%` 形式の変数を書けるようにし、「プロンプト＝テンプレート＋変数バインディング」というモデルにする。これで要件2・3・4を1つの仕組みに畳み込む。

### 変数の解決モード

各変数は次のいずれかで値に解決される。

| モード | 挙動 | 主な用途 |
|--------|------|----------|
| `fixed` | 固定値をそのまま使う | プリセット共通の定型句 |
| `random` | 候補リストから1個抽選 | 現行 `promptMode:"random"` / ランダム１行 / バリエーションの後継 |
| `input` | 実行前にユーザーが入力（未入力なら空 or デフォルト） | 服のはだけ具合など、キャラ依存で毎回変える箇所（要件3） |

### 生成時: バインディングの確定と記録

- 生成の各バッチで、使用中の全変数を解決モードに従って具体値へ解決する。`random` の抽選はここで1回だけ行う。
- 解決結果を**バインディングのスナップショット**として、画像1枚ごとの sidecar と `.seed-archive/` エントリへ保存する（現状 A案として検討していた「抽選結果の明示記録」がこれに一本化される）。
- 併せて、使用プリセットのIDと当時のテンプレート断片も保存し、プリセット定義が後から編集されても再現できるようにする。

### 引き継ぎ時: バインディングの再適用と部分上書き

- 引き継ぎ元エントリのバインディング・スナップショットを初期値として読み込む。
- **既定は全変数そのまま再適用**（＝要件2: その他・ランダム１行・バリエーションが引き継ぎ元と一致）。
- 継承プレビューで任意の変数を上書きできる。上書きは、同名変数が出現する**全プリセット・全バッチへ既定で適用**（＝要件4）。「この1件だけ」を選べるトグルも用意。
- 服装依存の箇所は `input` モードの変数にしておけば、引き継ぎ先で新しい値を入れるだけで済む（＝要件3）。同義グループ表や服装コンテキストの自動推定は不要。任意で「よく使う値」の候補リストを変数に添えて入力補助にできる（同義グループの軽量版）。

### 事前に `%%` を打っていない箇所

引き継ぎ時になって「ここも変えたい」と気づくケース向けに、継承プレビューへ**解決後プロンプトに対する一括 find & replace** を用意する（テンプレート編集不要のエスケープハッチ）。

## UI

### 1. 一括キュー実行画面: 変数入力ステップ

`BatchQueueDialog` の run-setup 前後に変数入力ステップを追加する。

- 選択中の一括キューセットに含まれる全プリセット（`other` 中心だが全スロット対象）と追加プロンプトを走査し、出現する `%%name%%` を集約する。
- `input` モードで未バインドのもの、または引き継ぎ元から値が来ていないものを入力対象としてリスト表示する。
- 各変数に**使用箇所バッジ**を付ける。バッジのラベルはプリセット名（＋スロット種別）。
  - マウスオーバーのツールチップで、その変数を含む**該当行（アイテムのプロンプト断片）**を表示する。
  - 同じ変数が複数プリセットで使われていればバッジを複数並べる。
- 入力欄は1変数につき1つ。ここで入れた値が全使用箇所に適用される（要件4）。候補リスト付きの変数はセレクト＋自由入力。

### 2. 通常の1枚生成モード: 変数バインディングのフローティングウィンドウ

一括キュー実行前のテスト生成でも同じ変数を触れるように、`ETA` ウィンドウと同じ仕組み（[floating-window.tsx](../../components/gallery/floating-window.tsx) を再利用）でフローティングウィンドウを出す。

- 現在チェックされているプリセット群から `%%name%%` を集約し、バインディングが必要な変数を一覧・その場で編集できる。
- タイトルバーの `badges` スロットに「未入力 N」等のバッジ。
- 編集した値は通常生成のプロンプト組み立てに反映され、`addToQueue` にも引き継がれる（テストで詰めた値をそのまま一括キューへ持ち込める）。
- 表示は「チェック中のプリセットに変数が1つ以上あるとき」だけ。無ければ出さない。

## データモデルへの影響（概略）

- `Preset` / 追加プロンプト: テキストはそのまま。`%%name%%` はレンダリング時に解決。変数のメタ（モード・候補・デフォルト）は別テーブル（`data/` の JSON）で名前引き。まず全変数をグローバル名前空間にする（同名＝同一変数）。
- `BatchPreset`: `variableValues?: Record<string, string>`（`input` モードの既定値／セット単位の上書き）を追加。
- `QueueItem`: 確定済みバインディング `resolvedBindings?: Record<string, string>` を追加し、メタデータ保存とプレビュー表示に使う。
- `SeedArchiveEntry` / `ImageMetadata`: `bindings?: Record<string, string>` と、使用プリセットのテンプレート・スナップショットを追加。旧エントリ（フィールド無し）は従来通り「数値seedのみ引き継ぎ」で動く（後方互換）。
- `assemblePositivePrompt` / `resolvePreset`（[use-pipeline-queue.ts:185](../../hooks/pipeline/use-pipeline-queue.ts#L185)）: 変数解決フェーズを差し込む。`random` 変数の抽選をここへ集約し、結果を呼び出し側へ返す。

## 段階実装

1. **Phase 1 — 変数エンジン**: `%%name%%` のパース・解決（`fixed`/`input`）、通常生成のフローティングウィンドウ、一括キューの変数入力ステップ（使用箇所バッジ＋ツールチップ含む）。まだseed引き継ぎ連携なし。既存の `promptMode:"random"` はそのまま温存。
2. **Phase 2 — 記録と引き継ぎ**: バインディングを sidecar / アーカイブへ保存。継承プレビューでバインディングを再適用＋部分上書き＋一括 find & replace（要件2・3・4）。
3. **Phase 3 — random 変数への移行**: `random` モードの変数を追加し、`promptMode:"random"` / ランダム１行 / バリエーションを変数へ寄せる（任意・後方互換を保ったまま段階移行）。

## 受け入れ基準（ドラフト）

- [ ] プリセット／追加プロンプトに `%%name%%` を書くと、生成時に解決され、`%%` を含まない既存プリセットは従来通り素通しされる
- [ ] 通常の1枚生成モードで、チェック中プリセットに変数があるときフローティングウィンドウが出て、値を編集すると生成プロンプトへ反映される（変数が無ければ出ない）
- [ ] 一括キュー実行画面で、選択セット内の全プリセットから変数が集約され、未入力のものが入力対象として並ぶ
- [ ] 各変数に使用箇所バッジが出て、マウスオーバーで該当アイテムのプロンプト断片がツールチップ表示される
- [ ] 1つの変数へ入力した値が、同名変数の全出現箇所（複数プリセット・全バッチ）へ適用される
- [ ] 生成した画像の sidecar / アーカイブに、確定したバインディングが保存される
- [ ] 引き継ぎ元と引き継ぎ先で「その他」プリセット選択・追加プロンプト・バリエーション設定が同一のとき、可変LoRA/身体的特徴/シーン以外の `positivePrompt` が引き継ぎ元と完全一致する（既定＝全バインディング再適用）
- [ ] 継承プレビューで特定の変数を上書きすると、その変数の全出現箇所へ反映される（「この1件だけ」を選んだ場合を除く）
- [ ] 継承プレビューの一括 find & replace で、変数化されていない箇所も解決後プロンプト上で置換できる
- [ ] バインディング情報を持たない旧アーカイブエントリでも、従来の「数値seedのみ引き継ぎ」が動く（後方互換）
- [ ] アーカイブ済みだが元フォルダが削除済みのケースでも上記が動作する

## 実装状況（2026-08-30 Phase 1〜3 実装済み）

コミット前の実装で以下を反映済み。提案からの差分は次の通り。

- **変数定義の保存先**: `data/` の JSON ではなく localStorage(`cp_variable_defs`)。アプリが全設定を localStorage で持つ既存方針に合わせた。エクスポート/インポート(`hooks/pipeline/use-pipeline-io.ts`)にも含めた。
- **変数定義の編集 UI**: 独立モーダルは作らず、変数リスト各行の歯車アイコンからモード/デフォルト値/候補をその場編集する形にした（通常モードのフローティングウィンドウ・一括キューの変数入力ステップ共通の `VariableBindingList`）。
- **通常モードのブロック**: 未入力の必須 `input` 変数があると「キューに追加」ボタンを無効化し、フローティングウィンドウに警告を出す。
- **一括実行(`BulkRunSetupView`)**: 変数入力ステップは通さない（提案どおりスコープ外）。`BatchPreset.variableValues` とデフォルト値のみで解決し、未入力の必須変数は空文字になる（ブロックしない）。
- 主なファイル: `lib/comfy/prompt-variables.ts`(エンジン), `test/unit/prompt-variables.test.ts`, `hooks/pipeline/pipeline-prompt-helpers.ts`(`resolvePromptVariables`), `hooks/pipeline/use-pipeline-queue.ts`(生成時解決＋メタデータ保存), `hooks/pipeline/use-variable-bindings.ts`, `components/pipeline/prompt/variable-binding-list.tsx` / `variable-binding-window.tsx`, `components/pipeline/queue/batch-queue-variable-input-view.tsx`, `lib/server/gallery-seed-archive.ts` / `gallery-seed-pool.ts`(bindings 永続化・引き継ぎ)。

## 確定事項（2026-08-30 ユーザー判断）

1. **構文**: `%%name%%`。変数名は `[A-Za-z0-9_]` のみ許可。
2. **未入力時の挙動**: `input` 変数が未入力なら、デフォルト値があればそれを使い、無ければ生成実行をブロックして入力を促す。
3. **スコープ**: グローバル名前空間（同名＝同一変数）。プリセットローカル変数は当面持たない。
4. **`BatchPreset.variableValues`**: セット単位の既定値。実行画面での入力はそれを一時上書きする。
5. **Phase 分割**: Phase 1〜3 をまとめて実装する。
6. **既存 `promptMode:"random"`**: 併存のまま・自動移行なし。`random` 変数は追加機能として共存させる。
